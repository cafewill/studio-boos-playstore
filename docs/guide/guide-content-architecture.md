# 🧱 공통 구조·계약·유지보수 가이드

## 📖 개요

모든 신규·수정 콘텐츠는 이 구조를 따른다. 등록 후보를 별도 코드베이스로 복제하지 않고 공통 셸·유형 엔진·선언형 콘텐츠 정의로 관리한다. 같은 엔진을 쓰는 문항 범위·그림 가이드·테마 변형과 새로운 상호작용 유형을 구분하여 집계한다. 후보 60개·MVP 정의 60개는 독립 게임 엔진 60개나 최종 검증 완료 60개를 뜻하지 않는다.

## 🧩 주요 내용

### 🗂 정본과 생성 파일

```text
data/implementation/registry.json     # 활성 배치 목록
data/implementation/batch60.json      # 현재 콘텐츠·후보 매핑·상태의 편집 원본
contents/
  catalog.js                         # 생성된 사용자 목록, 원작 정보·개발 상태 제외
  index.html / portal.js / portal.css # 사용자 포털과 필터
  shared/
    core/definition.js               # 정의 스키마와 지원 엔진
    core/model.js                    # 공통 상태·이벤트·버전·복원 계약
    core/storage.js                  # 저장·삭제·마이그레이션 경계
    core/utils.js                    # 시드·기하·색 데이터
    engines/                         # DOM 없는 활동 규칙 어댑터
    ui/                              # 공통 표시·포인터·SVG·사운드
    app.js / style.css               # 단일 셸과 디자인 토큰
  {slug}/
    content.js / index.html          # 생성된 정의·진입점
    src/main.js / README.md          # 생성된 공통 부트스트랩·설명
```

활성 배치는 `data/implementation/registry.json`에 등록하며 현재 정본 배치는 `batch60.json`과 `expansion40.json`이다. 각 배치 정의를 편집하고 `node tools/content/generate.mjs`로 생성 파일을 갱신한다. 생성 HTML·JS·README·catalog를 직접 편집하지 않는다. 카탈로그·진입 파일·설명의 수작업 중복 수정과 누락을 `generate.mjs --check`로 차단한다. 사용자 목록은 후보·원작명·작업 상태를 보여주지 않는다.

### 🔑 의존 방향과 책임

- 정의는 순수 데이터다. UI·저장·엔진 함수를 포함하지 않는다.
- 규칙 엔진은 데이터와 시드만 다루며 document·window·localStorage·AudioContext·fetch를 참조하지 않는다.
- model은 엔진을 호출해 공통 상태를 관리하고, storage만 브라우저 저장소 접근을 담당한다.
- UI는 상태를 표시하고 정해진 이벤트를 전달한다. 정답·진행 판정을 DOM에서 계산하거나 저장소를 직접 읽지 않는다.
- 공통 모듈은 개별 콘텐츠로 역참조하지 않는다. 콘텐츠 간 직접 import, 개별 CSS·셸·저장 코드 복제를 금지한다.
- 색·간격·포커스·버튼 상태·모션 감소·대화상자는 공통 UI에서 관리한다. 콘텐츠 차이는 정식 정의 필드와 등록된 엔진 동작으로 표현한다.
- 새로운 엔진이 필요하면 definition 등록·model 연결·stage 표시·검증·문서·영향 콘텐츠 목록을 같은 작업에서 갱신한다. 조용히 개별 main.js에 특수 분기를 넣지 않는다.

### 🔎 조건부 후보의 좁은 범위 확장

원본 조사 스냅샷의 판정을 수정해 후보 수를 부풀리지 않는다. 조건부 후보는 배치 항목의 scopeReview에 원래 상태·설명 근거·기존 독립 범위·이번 허용 범위·제외 요소를 기록한다. 검사기는 적합 후보 또는 이 기록이 있는 조건부 후보만 등록하며 보류·제외 후보는 허용하지 않는다. 출처 앱의 적합성 승격과 좁은 프로토타입의 구현 가능성을 구분한다.

새 엔진 words·routine·scene은 기존 상태·저장 계약에 추가 등록한다. 기존 엔진의 상태 의미는 변경하지 않아 engineVersion=1과 v2 저장 형식을 유지한다. 표시·로직·브라우저 시나리오를 함께 추가하고 이전 배치도 회귀 검사한다. batch60 이름을 가진 도구는 호환 경로이며 활성 레지스트리 전체를 대상으로 한다.

### 🎨 공통 구조와 시각 표현의 분리

알고리즘·상태·저장·입력 계약을 공유하는 것이 동일한 화면을 강제하지는 않는다. 기본 조작·접근성은 공통으로 유지하되, 활동 장면·구도·그림·배치·반응은 [UI 가이드](guide-ui-design.md)의 다양성 기준을 따른다. 동일 엔진에도 서로 다른 표시 구성이 필요할 수 있다.

향후 시각 변형은 검증 가능한 선언형 표시 정의와 등록된 표시 어댑터로 확장한다. 셸·CSS·저장 코드를 콘텐츠 폴더에 복제하지 않는다. 새 필드를 추가할 때 스키마·생성기·기본값·검사·기존 콘텐츠 호환을 함께 구현한다. 이는 후속 확장 원칙이며 현재 60개에 다양한 장면 어댑터가 모두 구현됐음을 뜻하지 않는다.

### 🖼 표시 데이터와 미술 안내선

정의의 description은 활동별 소개이며 카탈로그도 같은 값을 사용한다. 선택 필드 presentation은 미리보기의 짧은 설명·표시 기호만 담는다. catalog.preview는 공개 가능한 엔진·유형·params·presentation을 생성해 제공하고 원작 식별 정보는 제외한다. 카드와 시작 화면은 동일한 공통 artwork 함수를 호출한다.

미술의 SVG·Canvas 안내선은 ui/artwork.js의 DRAWING_PATHS를 공유해 미리보기와 실제 활동의 불일치를 방지한다. 문구·배경 안내선 변경은 규칙이나 저장 획의 의미를 변경하지 않아 기존 definitionVersion과 저장 버전을 유지한다. 기존 그림 위의 안내선 배경은 달라지므로 브라우저에서 복원 화면을 별도 확인한다.

### 🧩 콘텐츠 정의 계약

필수 필드는 schemaVersion·definitionVersion·slug·title·family·engine·variant·ageMin·ageMax·roundCount·objective·description·params·accent다. slug·범위·지원 유형·문항·버전은 definition.js로 검사한다. 원작 식별·후보 ID·참고 URL은 배치 원본의 조사 필드에 두고 생성된 사용자 정의에는 포함하지 않는다.

시드·같은 정의로 같은 문항을 생성한다. 문항 생성 방식·정답·목표 배열의 의미를 바꾸면 definitionVersion을 올리고 복원·마이그레이션을 검토한다. 테마만 바꾸는지 규칙을 바꾸는지 변경 계획에 명시한다.

### 🔄 상태·엔진 API

공통 세션은 version=2·contentId·definitionVersion·engineVersion·seed·phase·previous·round·data다. 시작 화면은 셸 상태이며 학습 데이터와 분리한다.

```text
시작 화면 → playing → feedback → 다음 문항 playing / complete
playing·feedback → paused → 원래 상태
complete → 명시적인 새로 시작
```

| 함수·역할 | 계약 |
|---|---|
| create(def, seed) | 재현 가능한 초기 엔진 데이터 반환 |
| act(data, event, def, round) | 새 데이터·안내 문구 반환, DOM·사운드·저장 부작용 없음 |
| done(data, round) | 해당 문항·창작 작업의 완료 여부 |
| validate(data, def, seed) | 복원 가능한 데이터인지 검사 |
| model.dispatch | pause·resume·next와 상태별 입력 차단, 엔진 이벤트 연결 |
| model.restore | 콘텐츠·정의·엔진 버전·진행·엔진 데이터 검사 후 정규화 |

오답은 진행을 유지하고 다시 시도하게 한다. 피드백·일시정지·완료 상태의 중복 활동 입력은 무시한다. 창작은 유일 정답을 강요하지 않으며 감정은 특정 선택을 오답으로 평가하지 않는다. 자유 그리기·조립·연주 등의 완료 조건은 개별 계획에 구체적으로 정의한다.

### 🔒 저장·마이그레이션

기본 키는 `{slug}:v2:session`·`{slug}:v2:sound`다. 실제 데이터가 어떤 콘텐츠·정의·엔진 버전인지도 검사한다. 다른 콘텐츠 데이터·미지원 버전·잘못된 좌표·비정상 단계는 복원하지 않는다. 저장소 차단 시 메모리 안에서 계속 실행한다.

저장 구조가 바뀌면 v3 등 새 키·명시적 변환·회귀 검증을 같은 작업에서 추가한다. localStorage.clear()와 공통 접두사의 무차별 삭제를 사용하지 않는다. 삭제는 해당 콘텐츠의 허용된 키에만 적용한다. 호환 변환은 storage 경계에서만 정의하고 UI에 버전 분기를 흩뿌리지 않는다.

모양 정원의 v1 진행·문항·선택 위치·소리 설정은 공통 v2로 변환한다. `balanced-v1` 생성 규칙을 보존하며 과거의 규칙 API는 shared/engines/shape-legacy.js에서 관리한다. 이전 경로 src/activity.js·src/storage.js는 생성된 과거 회귀 검사 전용 호환 경로이며 저장 동작도 공통 legacy-storage 서비스로 위임한다. 신규 코드는 이 경로를 사용하지 않는다. 이것이 현재 유일한 구조 예외이며 추가 예외는 사유·범위·검증·제거 조건을 기록하고 검사기를 함께 변경한다. 예외라는 이유만으로 사용자에게 반복 승인 요청을 하지 않는다.

### ✅ 구조 불일치 방지 검사

```bash
node tools/content/generate.mjs        # 명시적 생성
node tools/content/check.mjs           # 읽기 전용 정본·출처·구조·역참조·복제 검사
node tools/logic/batch60.mjs           # 전체 정의의 계약·규칙·저장·호환 검증
node tools/check-all.mjs               # 로직·데이터·문법·문서 전체 검사
```

새 배치 파일을 추가할 때 출처 스냅샷·후보 항목·reviewDocument·planDocument를 함께 지정하고 레지스트리에 등록한다. 생성 설명은 해당 배치의 리뷰 문서로 연결한다. 후보 수·카탈로그 수는 등록 배치로부터 계산하며 현재 60이라는 숫자를 검사기·포털에 고정하지 않는다. 원본 후보 전체를 선택하지 않는 배치는 selectedCandidateIds로 선택 범위를 명시한다. 현재는 후보당 MVP 한 개를 기본으로 하며 같은 후보의 복수 활동은 목표·중복·집계 규약을 검토한 뒤 정의 계약을 확장한다.

체크 항목은 후보 누락·중복, 카탈로그 누락, 엔진 미등록, 생성 파일 직접 수정, 개별 CSS/화면/저장 코드 증가, 공통 코드의 콘텐츠 역참조, 브라우저 의존 규칙, 시드 없는 무작위, 깨진 모듈·링크, MD/HTML 불일치다.

GitHub Actions의 `Content contracts and logic`가 push·PR에 같은 전체 검사를 실행하도록 구성했다. 서버/Chrome이 필요한 브라우저 검증은 별도이며 CI 구성만으로 원격 실행 성공이나 브라우저 완료로 표시하지 않는다. 워크플로는 읽기 권한만 사용하며 배포·자동 커밋을 수행하지 않는다.

### 🔄 변경 영향과 유지보수 순서

| 변경 위치 | 필수 확인 범위 |
|---|---|
| 콘텐츠 문항·목표·params | 해당 정의·버전·같은 유형의 경계 사례 |
| 엔진 규칙 | 그 엔진을 사용하는 모든 콘텐츠, 저장·완료·오답·시드 회귀 |
| 셸·model·storage·토큰 | 60개 전체 계약 검사, 7개 엔진 대표 브라우저 및 영향 콘텐츠 입력 검사 |
| schema·생성기 | 전체 생성·check·카탈로그·진입·설명 일치 |
| 저장 버전 | 기존 저장 fixture·지원 변환·차단·손상·다른 콘텐츠 데이터 보존 |
| 포털 | 60개 진입·검색·유형 필터·빈 결과·모바일·키보드 |

먼저 정본·영향 대상을 확인하고 규칙 또는 유형 설정을 바꾼다. 생성·회귀·문서 점검을 통과한 뒤 실제 브라우저에서 확인한다. CSS를 개별 경로에 붙이거나 같은 버그를 여러 main.js에서 각각 고치는 방식으로 해결하지 않는다.

### 🛡 배치 완료·권리·정서 기준

모든 후보를 일괄 추적하되 상태는 `검토 → 정의 → MVP → 로직 검증 → 브라우저 검증 → 리뷰 완료`로 나눈다. 대표 유형 테스트 성공을 모든 콘텐츠의 브라우저 성공으로 대신하지 않는다. 같은 엔진의 단순 변형을 새로운 메커닉으로 집계하지 않는다.

아동 정서·컬러·용어·네이밍·Fascinating·지식재산권 가이드는 공통 모듈과 개별 정의 모두에 적용한다. 원작 소스·브랜드·아트·문항·음원·화면 배열을 가져오는 대신 자체 도형·생성 규칙·문구를 사용한다. 자체 제작·교육 목적·공통 구조 사용을 법적 무위험이나 교육 효과 보증으로 표현하지 않는다.
